# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Finansal Risk & Portföy Analiz Platformu: lets a user inspect historical price data for BIST tickers (seeded with THYAO, ASELS, GARAN, TUPRS, AKBNK, but not limited to them — see "Dynamic asset universe" below), see per-asset risk/return/technical metrics, and build a weighted portfolio to analyze its combined performance. Three parts, developed independently:

- `backend/` — FastAPI REST API (Python)
- `frontend/` — React + TypeScript SPA (Vite), routed with `react-router-dom`
- `database/` — MS SQL Server (SQLEXPRESS locally); `database/schema.sql` is a manual-setup reference, but the backend is the source of truth for schema (see below)

There is no git repository yet — initialize one before making substantial changes.

## Commands

### Backend (run from `backend/`, using the repo-root `venv`)

```powershell
..\venv\Scripts\python.exe -m uvicorn main:app --reload --port 8000   # dev server, http://localhost:8000
..\venv\Scripts\python.exe -m pytest -q                                # run all tests
..\venv\Scripts\python.exe -m pytest test_analysis.py::test_max_drawdown -q   # run a single test
..\venv\Scripts\python.exe -m pip install -r requirements.txt          # install/update deps
..\venv\Scripts\python.exe -m data.seed_prices                         # (re)generate synthetic price history for the 5 seed tickers
```

Swagger UI is available at `http://localhost:8000/docs` when the dev server is running.

### Frontend (run from `frontend/`)

```powershell
npm install
npm run dev       # dev server, http://localhost:5173 (must be opened as "localhost", not 127.0.0.1 — Vite only binds the hostname)
npm run build     # tsc -b && vite build
npm run lint
npm run preview
npm test          # Vitest — unit/component tests
npm run test:e2e  # Playwright — real-browser tests; both npm run dev AND the backend must already be running
```

### Database

Local instance: `localhost\SQLEXPRESS` (Windows auth). ODBC Driver 18 is installed and requires encryption, so both `sqlcmd` and the app connection string need `TrustServerCertificate=yes` (already set in `backend/config.py`; for manual `sqlcmd` use, pass `-C`).

Tables are created/updated automatically on backend startup via `Base.metadata.create_all()` in `backend/database.py` — there is no separate migration tool configured. `database/schema.sql` mirrors the SQLAlchemy models for manual reference only; if you change a model in `backend/models/`, keep `schema.sql` in sync by hand.

Text columns that may hold non-ASCII (Turkish) characters must use `sqlalchemy.Unicode`, not `String`/`VARCHAR` — see `models/asset.py` and `models/portfolio.py`.

## Architecture

**Backend layering** — routers → services → models/analysis, with SQLAlchemy sessions injected via FastAPI `Depends(get_db)`:
- `backend/routers/` — FastAPI route handlers and Pydantic request/response schemas (one router module per resource: `auth.py`, `assets.py`, `portfolios.py`, `holdings.py`, `public.py`). Registered in `backend/main.py`. `routers/auth.py` also defines the `get_current_user`/`get_current_user_optional`/`get_current_user_and_session` dependencies used by any endpoint that needs a logged-in user, and owns 2FA, session-management, and activity-log endpoints (see "Auth: sessions, 2FA, audit log" below). `routers/public.py` is the one router with genuinely no auth dependency anywhere in it — see "Portfolio sharing" below.
- `backend/services/` — business logic and DB queries. Routers call services; services take a `Session` and return ORM objects or plain dicts.
  - `asset_service.py` — list/lookup `Asset` rows.
  - `price_service.py` — reads `PriceHistory` for an asset, and `refresh_price_history()` overwrites it with real OHLCV data via `market_data_provider`. Callers never query `PriceHistory` or yfinance directly.
  - `market_data_provider.py` — `fetch_ohlcv(yahoo_symbol, period)` fetches real daily OHLCV bars via `yfinance` (takes the asset's stored `yahoo_symbol` directly — it no longer assumes a `.IS` BIST suffix, since assets can now be any Yahoo Finance symbol). `search_symbols(query)` proxies Yahoo Finance's public, key-less search endpoint for the nav search bar. `get_currency(yahoo_symbol)` does a best-effort `fast_info` lookup (falls back to `"USD"`). `fetch_ohlcv_cached()` memoizes for `_CACHE_TTL_SECONDS` (15 min) — used for the `BIST100_SYMBOL` (`XU100.IS`) benchmark fetch in the portfolio-analysis endpoint so every portfolio view doesn't re-hit Yahoo Finance.
  - `analysis_service.py` — pure computation combining price data with `backend/analysis/portfolio_metrics.py` functions: `asset_analysis()` for a single ticker (includes `sharpe_ratio`), `portfolio_analysis()`/`portfolio_value_series()` for a weighted multi-asset index (normalized to start at 100, also includes `sharpe_ratio`), `correlation_matrix()` (pairwise Pearson correlation of constituent daily returns), `benchmark_index_series()` (aligns an arbitrary benchmark's raw prices onto the portfolio's own date axis and re-normalizes to base=100, so it can overlay directly on the portfolio index chart).
  - `portfolio_builder_service.py` — CRUD + validation for user-owned `Portfolio`/`PortfolioAsset` rows: `create_portfolio`, `update_portfolio` (replaces all `PortfolioAsset` rows, also accepts optional `benchmark_symbol`/`benchmark_label`), `delete_portfolio` (returns `False` if not found/not owned rather than raising; also nulls out any `Holding`/`HoldingSale` rows that referenced it, required now that `holdings.portfolio_id` carries a real FK — see "Migrations" above). Weights must sum to 100, no negative/duplicate/unknown tickers — see `validate_portfolio_input`, tested against an in-memory SQLite DB in `test_portfolio_validation.py` and `test_portfolio_management.py`. Also owns `compute_portfolio_analysis_payload()` (the actual `/analysis` computation, shared verbatim by the owner route and the public share route — see "Portfolio sharing" below) and `generate_share_link()`/`revoke_share_link()`/`get_portfolio_by_share_token()`.
  - `portfolio_service.py` / `auth_service.py` — `Holding` (manual buy-transaction tracking) CRUD, ownership-checked `update_holding`/`delete_holding`, and `value_holding()`/`valuation_summary()` which attach live valuation (current price via `asset_service`/`price_service`, cost basis, market value, unrealized P&L/%) to holdings — this is the data source for the "Pozisyonlar" panel in `PortfolioBuilder.tsx`. `realized_pl_by_year()` groups `sell_holding()`'s already-computed FIFO realized sales by calendar year and ticker — see "Tax report" below. `auth_service.py` is JWT/password auth plus TOTP 2FA and session issuance/validation — see "Auth: sessions, 2FA, audit log" below.
- `backend/models/` — SQLAlchemy ORM models (`Base` subclasses), re-exported from `backend/models/__init__.py`. Key relations: `PriceHistory.asset_id → Asset`, `Portfolio.user_id → User`, `PortfolioAsset.{portfolio_id → Portfolio, asset_id → Asset}`. `PriceHistory` stores full OHLCV (`open_price`, `high_price`, `low_price`, `close_price`, `volume`), not just close — needed for the candlestick chart on `/assets`. `Asset` has `ticker` (unique display symbol), `yahoo_symbol` (what's actually passed to yfinance — may differ from `ticker`, e.g. `THYAO` / `THYAO.IS`), `exchange`, and `currency` (`"TRY"`, `"USD"`, etc. — always render prices through this, never assume ₺; see `frontend/src/lib/currency.ts`).
- `backend/analysis/` — pure, DB-independent numeric functions over `pandas`/`numpy` (returns, volatility, Sharpe ratio, drawdown, allocation) — these only ever operate on the close-price series. No FastAPI or SQLAlchemy imports here; keep this module framework-agnostic so it stays independently testable.
- `backend/data/seed_prices.py` — generates ~1 year of synthetic (seeded random-walk) daily OHLCV bars for the 5 tickers and upserts them via `Asset`/`PriceHistory`. Run with `python -m data.seed_prices` from `backend/`.
- `backend/database.py` — engine/session setup; `backend/config.py` builds the MSSQL connection string (pydantic-settings, reads `backend/.env`) from the `MSSQL_*` fields, unless `DATABASE_URL` is set, in which case it's used verbatim instead (e.g. `postgresql+psycopg2://...` for a managed Postgres instance that can't reach a local SQL Server — see "Deployment" below). `database.py`'s `create_all()`/`run_light_migrations()` already dialect-branch on `engine.dialect.name` (`mssql` vs. everything else, for `BIT` vs. `BOOLEAN` column DDL), so pointing `DATABASE_URL` at Postgres needs no other backend code change to provision its schema from scratch on first boot — only `backend/migrations/versions/*.py`'s two files that reference `sqlalchemy.dialects.mssql` are MSSQL-specific and shouldn't be replayed against a non-MSSQL target; a fresh non-MSSQL database should rely on `create_all()` for its initial schema (same bootstrap precedent as the original MSSQL baseline — see "Migrations (Alembic)" above) rather than `alembic upgrade head`.

Config is env-driven: copy `backend/.env.example` to `backend/.env` and `frontend/.env.example` to `frontend/.env.local` for local overrides.

**Migrations (Alembic)**: `backend/migrations/` is a real Alembic setup — `migrations/env.py` points `target_metadata` at `Base.metadata` (via `import models`, which populates it as a side effect) and builds its connection URL from `config.settings.sqlalchemy_database_url` rather than `alembic.ini`'s placeholder, so it always talks to whatever DB the app itself would connect to. For any new table or column going forward, prefer `python -m alembic revision --autogenerate -m "..."` (from `backend/`) + review the generated script + `python -m alembic upgrade head` over hand-writing DDL. The dev DB was baselined by autogenerating a migration against the already-`create_all()`'d schema and running `alembic stamp head` (marks it current without executing DDL) rather than `upgrade head`, so a fresh clone/deploy should run `alembic upgrade head` after its first `create_all()` to reach the same state. `Base.metadata.create_all()` in `main.py` still runs on every startup and still only creates *missing* tables — it never alters an existing one, so Alembic is what actually carries a column/constraint change forward from here. The pre-Alembic mechanism, `database._add_column_if_missing()` inside `run_light_migrations()`, is **not removed** — its existing two call sites (`holdings.portfolio_id`, `assets.is_default`/`sector`, `users.email_alerts_enabled`) stay as-is for already-deployed installs that upgrade straight from before Alembic existed, but don't add new columns through it; use Alembic instead. Note the baseline autogenerate diff surfaced that `holdings.portfolio_id` (added via the light-migration path) has no FK constraint or index in the live dev DB the way a fresh `create_all()` table would — `migrations/versions/0512b890af99_*.py` captures the fix (add the FK+index, tighten two backfilled columns to `NOT NULL`) but was deliberately left un-applied (baseline was stamped, not upgraded) rather than altering the dev DB's live schema without an explicit decision to do so; run `alembic upgrade head` when ready to actually apply it.

**Auto-refresh (backend) / live data (WebSocket, not client polling)**: `main.py`'s `lifespan` starts three `asyncio` background loops — `_auto_refresh_loop` calls `price_service.refresh_price_history()` for every tracked asset every `AUTO_REFRESH_INTERVAL_SECONDS` (30s — Yahoo Finance itself still isn't a tick-level feed, so this is closer to a fast poll than a real real-time feed, but it keeps DB-backed price history as fresh as the loop can practically make it; each asset's fetch is staggered by a small random `AUTO_REFRESH_JITTER_SECONDS` delay rather than fired as a synchronized burst, and the per-asset `try/except` catches any exception — not just the "no data" `ValueError` — so a transient Yahoo Finance rate-limit/network error on one asset can't wipe out that tick's refresh for every other asset; raise the interval back toward 5 min, or move to refreshing a rotating batch of assets per tick, if Yahoo Finance rate-limiting is observed in practice), `_market_data_broadcast_loop` re-reads the reference-data endpoints' own in-process cache every 60s (ticker-strip/indices/commodities/crypto/crypto-global/fx), and `_news_broadcast_loop` every 5 min. All three are plain `asyncio.sleep` loops, not a job scheduler library, and all their yfinance/requests calls run via `asyncio.to_thread` so a slow Yahoo round-trip doesn't stall the event loop (and every request/WebSocket connection this worker is serving) for its duration. Rather than clients independently polling `GET` endpoints on their own interval (the old design, `useAutoRefresh.ts`, now deleted), every one of these loops **pushes** its result over a single shared WebSocket at `GET/WS /ws` — real transport, not a rename: the client already has the data the instant the backend does, instead of up to `intervalMs` late, and N browser tabs no longer each independently re-trigger the same fetch.
  - **Backend**: `services/ws_manager.py`'s `ConnectionManager` (module-level singleton `manager`) tracks every connected `WebSocket` and which named channels each subscribed to (`quotes`, `ticker-strip`, `indices`, `commodities`, `crypto`, `crypto-global`, `fx`, `news`, `prices-updated`, and the per-user `alerts`). `routers/ws.py`'s `/ws` endpoint accepts an optional `?token=<JWT>` query param (a browser `WebSocket` can't set an `Authorization` header, so this is the pragmatic equivalent — reuses `auth_service.decode_access_token`, no DB hit needed) and then just relays `{"action": "subscribe"|"unsubscribe", "channels": [...]}` client messages into the manager. `alert_service.check_alerts_for_asset()` now returns the newly-triggered `PriceAlert` rows (not just a count) specifically so `_auto_refresh_loop` can `send_to_user()` each one straight to its owner's `alerts` channel the instant it fires. `routers/markets.py`'s REST handlers are now thin wrappers around `compute_*()` functions (`compute_ticker_strip`, `compute_crypto_quotes`, `compute_market_news`, ...) so the broadcast loops and the REST endpoints share one implementation instead of two. **Multi-worker fanout (optional Redis)**: without `REDIS_URL` set, broadcasts only reach clients connected to the same uvicorn worker process — exactly right for this app's default single-worker dev/deploy setup. With it set, `services/redis_client.py` (a soft dependency — every function returns `None`/`False` rather than raising if Redis is unset or unreachable, so a Redis outage degrades this worker back to local-only delivery instead of crashing) backs `ConnectionManager.broadcast()`/`send_to_user()`: instead of delivering to local connections directly, they publish an envelope to one shared Redis channel (`pa:ws:broadcast`), and `ws_manager.redis_relay_loop()` (started unconditionally in `main.py`'s lifespan alongside the other background loops, a no-op task if Redis isn't configured) is the *only* thing that actually delivers to local connections — every worker, including the one that published, goes through this same relay, so there's one delivery path regardless of process count rather than two racing ones. Tested against `fakeredis.FakeAsyncRedis` (a real in-process pub/sub implementation, not a call-count mock) in `test_ws_redis_relay.py` — no real Redis server needed to verify the relay logic itself, only to actually run it multi-worker. Note this only solves the *WebSocket fanout* half of a multi-worker deployment; `market_data_provider.py`'s in-process caches (`_ohlcv_cache`, `_news_cache`, ...) are a separate, still-open piece — each worker would independently re-fetch from Yahoo/CoinGecko rather than sharing one Redis-backed cache, deliberately not tackled in the same pass since migrating five different cache shapes blind (no live Redis available to verify against at the time) carried more regression risk than the fanout piece alone.
  - **Frontend**: `src/lib/LiveDataContext.tsx`'s `LiveDataProvider` (mounted once in `App.tsx`, `key={token ?? 'anon'}` so logging in/out remounts it — a fresh connection carrying the current auth token is simpler and more robust than trying to swap a token on a live socket) owns the one shared `WebSocket` for the whole app, auto-reconnects with exponential backoff (capped at 30s), and re-sends every still-wanted channel's subscription on reconnect. Components never touch the socket directly — `src/lib/useLiveChannel.ts` exports `useLiveChannel<T>(channel)` (returns the latest payload, for snapshot-style channels like quotes/news) and `useLiveSignal(channel, onSignal)` (fires a callback with no payload, for `prices-updated` — a portfolio/holdings view re-fetches its own REST-computed valuation on this signal rather than the server pushing that expensive computation, correlation matrices included, to every open tab on every price refresh). Multiple components subscribing to the same channel share one underlying server subscription (reference-counted in the provider). `NotificationBell.tsx` is the one consumer that subscribes to `useLiveData()` directly instead of through those two hooks, since a triggered alert is a discrete event to prepend to a list, not a snapshot to replace it with.
  - **A real bug this surfaced**: `market_data_provider.fetch_ohlcv_cached()`'s in-process cache was keyed by symbol alone, not `(symbol, period)`. `get_quote()` calls it with `period="5d"` for lightweight quotes; once `_market_data_broadcast_loop` started calling `get_quote("XU100.IS")` every 60s (for the ticker strip), it kept overwriting the *same* cache entry the BIST 100 history chart and the portfolio benchmark overlay expect to hold a full year — silently truncating both to 5 days' worth of data until the 15-minute TTL happened to expire. Fixed by keying the cache on `(symbol, period)`; regression-tested in `test_market_data_provider.py`. Watch for the same class of bug anywhere else a shared cache is keyed on less than its full set of call-site-varying parameters.

**Risk-free rate for Sharpe ratio**: `analysis_service.RISK_FREE_RATES` is a hand-set dict of rough annual rate assumptions by currency (`TRY: 0.45`, `USD: 0.045`, etc.) — not a live rate feed (none is available), but an explicit, documented assumption rather than silently treating every currency as 0%. `risk_free_rate_for(currency)` looks it up (defaults to 0.0 for unmapped currencies); portfolios blend it by constituent weight in `routers/portfolios.py`. Update the dict if the assumption goes stale rather than wiring in an unlicensed "live" source.

**Frontend**: routed via `react-router-dom` in `App.tsx` (`/` Home, `/market` MarketDashboard, `/assets` AssetScreener, `/assets/:ticker` AssetDetail, `/portfolio` PortfolioBuilder — gated behind `LoginForm` when not authenticated, `/kripto` CryptoLeaderboard, `/enflasyon` InflationMap — see "Reference-data endpoints" below for the last two). `src/api.ts` is the only place that talks to the backend (typed `fetch` wrappers); keep new backend calls there rather than scattering `fetch` calls across components. `src/pages/` holds the routed pages, `src/components/` holds shared UI (`Layout` nav shell, `Card` stat tile, `Watchlist` sidebar list), `src/lib/indicators.ts` holds pure client-side calculations (SMA, RSI, period returns) over a close-price series — no backend round-trip needed since the full price series is already in hand. `src/charts/LineChart.tsx` wraps `react-chartjs-2`/Chart.js for line charts, `src/charts/CandlestickChart.tsx` is a hand-rolled Canvas 2D candlestick+volume chart (own crosshair/tooltip/range-tabs state, no external charting lib). Both chart components read colors from the CSS custom properties in `index.css` (`--success`/`--danger`/`--primary`/etc.) via `getComputedStyle` at render time — never hardcode a chart color, add/reuse a token instead so charts stay in sync with the palette. Auth token lives in `localStorage` via `src/auth.ts`. The `Holding` CRUD feature (`getHoldings`/`createHolding` in `api.ts`) is wired into the UI via `src/components/HoldingsPanel.tsx`, rendered as the "Pozisyonlar" section of `PortfolioBuilder.tsx` — this is the real buy-transaction tracker (ticker/quantity/purchase price/date) that `RebalancingSection` and the valuation summary (`valuation_summary()`) key off of; despite the name it's a fully-live feature, not the dead one an earlier version of this file described. Any unmatched route falls through to `pages/NotFound.tsx` (a plain "Sayfa bulunamadı" card, not a blank page) via a catch-all `<Route path="*">` at the end of `App.tsx`'s route list.

**Asset pages are a real two-level site, not one page with a dropdown**: `/assets` (`AssetScreener.tsx`) is a sortable comparison table of all tickers (click any column header to sort; click a row to navigate to `/assets/:ticker`). `/assets/:ticker` (`AssetDetail.tsx`) is the per-symbol page — breadcrumb, a sticky `Watchlist` sidebar (ticker/name/last price/day change, fed by `GET /assets/quotes`, a lightweight batched-quote endpoint distinct from the heavier per-ticker `/analysis` endpoint) that navigates between symbols via `useNavigate`, a price header, the summary card-grid, and four tabs — **Genel Bakış** (the `CandlestickChart` + daily-return chart + price table), **Teknikler** (SMA 20/50/200 and RSI(14), computed client-side via `src/lib/indicators.ts` from `analysis.prices`, each with a plain-language signal like "Fiyat üzerinde" — never fabricated, always derived from real OHLCV, and captioned "Yatırım tavsiyesi değildir"), **Performans** (a return grid across 1G/1H/1A/3A/6A/YBB/1Y/Tümü windows via `periodReturn()` — only windows the ~1y of history actually supports; don't add a 5Y/10Y window without more history behind it), and **Temeller** (valuation ratios, analyst recommendations, earnings calendar, institutional holders — see "Temeller tab" below; added once backed by a real free data source (yfinance), lazily fetched only when the tab is opened). This structure — and the `/market` page's card grid + comparison panel — is intentionally modeled on the *layout conventions* common to trading-terminal/markets sites (watchlist + chart + detail panel, a listing page linking into per-symbol pages with tabs), studied from tradingview.com for structural reference only; no TradingView copy, icons, logos, financial data, or code were copied — all visuals, text, computations, and colors here are original, run on this project's own data, and follow its own gold/dark palette. Don't add tabs/sections (news, community posts, ...) that would require fabricating data we don't have — every number on these pages must be real or computed from real data.

**Design system**: dark is the default and original look (a professional trading-terminal palette, not blue — deliberately warm gold instead), but the app also ships an opt-in **light theme**, toggled from the topbar (☀️/🌙 button next to the notification bell). `index.css`'s `:root` defines the dark palette (unchanged from the original single-theme design: `--bg: #0a0e14`, `--surface`/`--surface-2`/`--surface-3` step up in lightness, `--primary: #c9a15f` with `--primary-ink` for text on a gold background); a `:root[data-theme='light']` block overrides every token with a light equivalent (`--bg: #f4f5f7`, `--surface: #ffffff` and darker as surfaces step away from it, `--text-h`/`--text`/`--text-muted`/`--text-faint` inverted dark→light, `--success`/`--danger` darkened for WCAG AA contrast on white, `--primary`/`--primary-hover` darkened to a bronze-gold with `--primary-ink: #ffffff` — dark mode's bright gold+near-black-ink pairing falls under AA contrast as plain text on a white page). This is a manual toggle, not a `prefers-color-scheme` branch — `src/lib/ThemeContext.tsx`'s `ThemeProvider`/`useTheme()` hold the current theme in React state, sync it to `<html data-theme>` and `localStorage` (`pa_theme`), and `index.html` has a tiny inline blocking `<script>` that applies a saved `light` choice before first paint so there's no flash of the wrong theme on load. Typography is IBM Plex Sans (UI/headings) + IBM Plex Mono (`--mono`, for prices/tickers/tabular data — pair with `font-variant-numeric: tabular-nums`), loaded via a Google Fonts `@import` at the top of `index.css` (must stay before `@import 'tailwindcss'` — CSS requires `@import`s first). This same palette and type pairing is shared by the standalone single-file tool sent to the user earlier (`hisse-grafigi.html`, not part of this repo) — keep new UI consistent with it if referenced.

Two parallel styling systems coexist by design, both reading the same `index.css` tokens (and both theme-aware as a result): `Home`/`AssetAnalysis`/`PortfolioBuilder`/`LoginForm` use hand-written CSS (`App.css`, BEM-ish class names, `var(--token)`). The `/market` page (`src/components/ui/asset-market-dashboard.tsx` + `background-plus.tsx` + `FxTicker.tsx`) uses Tailwind CSS v4 (via `@tailwindcss/vite`) + framer-motion + lucide-react, following shadcn's conventions (`components.json`, `src/lib/utils.ts`'s `cn()`, `src/components/ui/` as the default component path, `@/*` path alias to `src/`) — since Tailwind v4 doesn't auto-map arbitrary CSS vars to color names, this page references the palette through the `@theme` bridge in `index.css` (`--color-surface` → Tailwind's `bg-surface`/`text-surface`/etc., one entry per token) rather than hardcoding hex; a handful of spots that need a literal color string where Tailwind classes can't reach (inline SVG `fill`/`stroke`, `BackgroundPlus`'s `plusColor` prop) use `var(--token)` directly, which browsers resolve fine in SVG presentation attributes. **Chart.js and hand-rolled `<canvas>` components are the one exception** — a canvas 2D context's `fillStyle`/`strokeStyle` cannot resolve `var()`, so `LineChart.tsx`/`DonutChart.tsx`/`EfficientFrontierChart.tsx`/`CandlestickChart.tsx` read tokens via `getComputedStyle(document.documentElement)` at render time (a `readToken()` helper) and additionally call `useTheme()` themselves purely to force a re-render (and thus a fresh token read) when the user flips the toggle — a `data-theme` attribute change is a DOM mutation outside React's own re-render tracking, so without this a chart already on screen would keep its stale theme's colors until something else caused it to re-render. `PortfolioBuilder.tsx` and `AssetDetail.tsx` each have one spot doing the same `getComputedStyle`-plus-`useTheme()` read for a single chart-line color (`--danger`) passed into `LineChart`. Multi-series accent palettes (`LineChart`'s/`DonutChart`'s/`AssetCompare`'s own `PALETTE` arrays, `TickerAvatar`/`avatar.ts`'s monogram colors) are deliberately *not* forked per theme — they're saturated, mutually-distinguishing hues that read fine against both a near-black and a near-white background, unlike `--primary`/`--success`/`--danger` used as small text. `InflationMap.tsx`'s globe visualization (ocean/graticule/space background) also deliberately stays a fixed dark "space" palette regardless of page theme — like an embedded video player's black bars, a 3D globe floating in space reads oddly re-themed to white. When adding new shadcn-style components, put them in `src/components/ui/`; when touching the older pages, stick to the existing plain-CSS classes rather than introducing Tailwind there. Any new component reading colors on a `<canvas>` (2D context or WebGL) must follow the `useTheme()` + `getComputedStyle` pattern above, or it will silently freeze on whichever theme was active when it first mounted.

Piyasa Görünümü (`/market`) also has a **Performans Karşılaştırması** panel (bottom of `asset-market-dashboard.tsx`) — a multi-asset normalized-% overlay chart (via `LineChart`) with range tabs (1M/3M/6M/1Y/ALL, client-side date filtering, same pattern as `CandlestickChart`) and per-ticker toggle chips, driven by `buildComparisonSeries()`. It reuses the full `AssetAnalysis` objects already fetched for the cards (kept in `analysesByTicker` state) rather than making extra API calls. Above the grid, a toolbar (search filter, sort dropdown, Kart/Tablo view toggle, `.live-indicator` "Son güncelleme" dot) filters/sorts the same `cards` array client-side (`visibleCards`, `sortCards()`) — `AssetTable` is the flat-table alternative to the card grid, same data, no extra fetch.

**Portföy Analizi (`PortfolioBuilder.tsx`) is a full analysis tool, not just a form**: selecting a portfolio calls `GET /portfolios/{id}/analysis`, which now returns `weights` (fractions, for the allocation `DonutChart`), `correlation` (from `analysis_service.correlation_matrix()`, rendered as a color-coded `.correlation-table` — green tones for low/negative correlation, red for high), and a best-effort `benchmark`/`benchmark_label` (`portfolio.benchmark_symbol or BIST100_SYMBOL`, wrapped in `try/except` server-side so a Yahoo Finance hiccup degrades to an empty array rather than breaking the whole analysis — the frontend shows a note instead of the overlay line when `benchmark` is empty; see "Custom benchmark" below). **Custom benchmark**: `Portfolio.benchmark_symbol`/`benchmark_label` (both nullable) override the `BIST100_SYMBOL` default per portfolio — set via the "Kıyas endeksi" dropdown in `PortfolioBuilder.tsx`'s create/edit form. **Base currency preference (Görüntüleme Para Birimi)**: `User.base_currency` (default `"TRY"`, one of `TRY`/`USD`/`EUR`/`GBP`, updated via `PUT /auth/me/currency`) replaces the old hardcoded `AGGREGATE_CURRENCY` constant for a given request — `portfolio_service.value_holding()`/`dividend_history()`/`holdings_value_history()` all now take an `aggregate_currency` parameter (still defaulting to `"TRY"` for direct/test callers), threaded from `current_user.base_currency` in `routers/holdings.py`. Set via `AccountSettings.tsx`'s `CurrencySection`.

**Portfolio sharing**: `Portfolio.share_token` (nullable, unique, random `secrets.token_urlsafe(32)`) enables `GET /public/portfolios/{token}/analysis` — a genuinely unauthenticated route (`routers/public.py`, no `get_current_user` anywhere in it, rate-limited via `rate_limit.throttle`) that returns the exact same payload `compute_portfolio_analysis_payload()` produces for the owner, which is safe to expose without auth by construction: that payload never contained holdings, cost basis, or any other personal financial data to begin with, so there's no second filtering pass that could drift out of sync. `POST/DELETE /portfolios/{id}/share` (owner-only) generate/revoke the link — regenerating invalidates any previously-issued token. **Tax report (Vergi Raporu, `/vergi-raporu`)**: `portfolio_service.realized_pl_by_year()` groups the same FIFO-computed `HoldingSale` rows `realized_pl_summary()` already sums (see "Temettü Takvimi" for the parallel real-only-data philosophy) by calendar year and, within each year, by ticker — no new computation, purely a grouping/reshaping pass. `GET /holdings/sales/tax-report` (optional `year` query param) backs `pages/TaxReport.tsx` (lazy-loaded, authenticated, linked from `HoldingsPanel.tsx`'s realized-P&L header) — year tabs, summary cards, a per-ticker table, CSV export. Explicitly framed in its own copy as computed from existing sale records, not an official/filed tax document.

**Risk-parity optimization**: a third objective alongside `max_sharpe`/`min_variance` — `analysis/portfolio_metrics.risk_parity_weights()` solves for long-only weights where every constituent contributes an equal share of total portfolio variance (via `scipy.optimize.minimize` on the sum of squared risk-contribution deviations, same SLSQP/equal-weight-fallback setup as the other two objectives), dispatched from `optimize_portfolio_weights(objective="risk_parity")` and validated in `routers/portfolios.py`'s `/optimize` endpoint. `PortfolioBuilder.tsx`'s `OptimizationSection` gets a third "Risk Paritesi" tab alongside the existing two — same `PortfolioOptimization` response shape, no separate frontend code path.

**Candlestick SMA overlay**: `CandlestickChart.tsx` accepts an optional `smaOverlays?: number[]` prop (e.g. `[20, 50]`) — computed via the existing `lib/indicators.ts` `sma()` (same function the separate Teknikler tab already uses) from the *full* unclipped price history, then looked up by date to align with whatever range (`1M`/`3M`/.../`ALL`) is currently clipped for display, so a short range still shows an accurate long-period average rather than nothing. **Dynamic asset universe**: the 5 seeded BIST tickers are a starting point, not a hard limit. `SymbolSearch.tsx` (mounted in `Layout.tsx`'s topbar, on every page, Ctrl+K to focus) debounce-searches `GET /assets/search?q=` (proxies Yahoo Finance search — any global equity/ETF, not just BIST) and lets the user track a result via `POST /assets/track`, which creates the `Asset` row and immediately backfills ~1y of OHLCV before returning — the new symbol is then a first-class asset everywhere (Piyasa Görünümü, the `/assets` screener, every `Watchlist`, the Portföy Analizi asset dropdown) with no further wiring, since all of those already just call `getAssets()`/`getAssetQuotes()` rather than assuming a fixed list. **Frontend tests**: `npm test` runs Vitest (`vitest.config.ts`, separate from `vite.config.ts` so the test setup doesn't affect the dev/build config; jsdom environment, `src/test/setup.ts` wires up `@testing-library/jest-dom` and — since `vitest.config.ts` doesn't set `test.globals: true` — an explicit `afterEach(cleanup)`, without which multiple `render()` calls across `it` blocks in one file silently accumulate DOM from prior tests instead of starting fresh). Test files are co-located as `*.test.ts(x)` next to the code they cover and excluded from `tsconfig.app.json` (see its `exclude`) so `npm run build`'s `tsc -b` doesn't try to type-check them against the app's stricter config. Existing coverage is intentionally narrow but real: pure logic in `src/lib/` (`indicators.test.ts`, `currency.test.ts`, `avatar.test.ts`), light component smoke tests (`Card.test.tsx`, `ErrorBoundary.test.tsx`), and one small context test (`ThemeContext.test.tsx`) — follow this pattern (pure functions get thorough unit tests, components get a light render-and-assert smoke test) rather than trying to snapshot-test the heavily-animated Tailwind pages.

**End-to-end tests (Playwright, `frontend/e2e/`)**: `npm run test:e2e` runs real-browser specs against the servers you already have running — `playwright.config.ts` points `baseURL` at `http://localhost:5173` and deliberately has no `webServer` auto-start block, since auto-starting Vite but not the Python backend would just produce confusing "backend unreachable" failures instead of a clear "start both servers first" message; there's no CI pipeline wired up yet either, so this is the automated analogue of the manual browser QA this project's been built with, not (yet) a merge gate. `home.spec.ts` and `navigation.spec.ts` cover public pages only (hero content actually populated with real market data, the theme toggle, every nav link routing to a real page, the 404 fallback, the `/portfolio` login-gate); `auth.spec.ts` registers a fresh throwaway account per run rather than depending on a fixture user, and deliberately uses `@playwright-e2e-mail.com` as the fake domain — `@example.com`/`.test`/`.invalid` are RFC 2606 reserved names that Pydantic's `EmailStr` (via `email-validator`) rejects at the syntax level even with deliverability checking off, which silently broke the very first version of this spec. Chromium only for now (`npx playwright install chromium --with-deps` to fetch the browser binary); add Firefox/WebKit `projects` in the config if cross-browser coverage becomes worth the extra install/run time.

**Error tracking (Sentry, optional)**: both `sentry_sdk.init()` (`backend/main.py`, top of the file, before `Base.metadata.create_all()`) and `Sentry.init()` (`frontend/src/main.tsx`, before the render call) read their DSN from `SENTRY_DSN`/`VITE_SENTRY_DSN` — Sentry's own SDKs treat an empty/missing DSN as "disabled" and every `Sentry.*`/`sentry_sdk.*` call becomes a documented no-op, so the app behaves identically configured or not; get a free DSN per-project at sentry.io and set it in `backend/.env`/`frontend/.env.local` to actually turn it on (`send_default_pii=False`/`sendDefaultPii: false` on both sides — this app handles real user emails, so PII forwarding is opt-in only, never a default). The FastAPI/Starlette integration only ever sees exceptions raised inside a request handler — it has no visibility into `main.py`'s standalone `asyncio.create_task()` background loops (`_auto_refresh_loop`, `_market_data_broadcast_loop`, `_news_broadcast_loop`, `ws_manager.redis_relay_loop`), so each of those has an explicit `sentry_sdk.capture_exception(exc)` in its own `except` block — and `_auto_refresh_loop` specifically gained an outer `except Exception` it didn't have before (previously, any error beyond the already-handled per-asset `ValueError` would propagate out of the `while True` and permanently kill that background task for the rest of the process's life, with nothing surfaced anywhere pointing at why prices had silently stopped updating). On the frontend, `ErrorBoundary.tsx`'s `componentDidCatch` calls `Sentry.captureException` — the one place a React render-time error is observable at all, since it never reaches `window.onerror`.

**Error boundary**: `src/components/ErrorBoundary.tsx` wraps `<Routes>` in `App.tsx` (inside `Layout`, so the topbar/nav/footer survive a crash) and renders a Turkish "Bir şeyler ters gitti" fallback with a reload button instead of a blank white page. It does not auto-reset on navigation (an error boundary's state doesn't clear just because a route changes) — "Sayfayı Yenile" does a full `window.location.reload()`, which is the deliberate, simple recovery path here rather than route-aware reset logic.

**Layout / sticky footer**: `Layout.tsx` renders `<Footer />` as a sibling of `<main className="content">` inside `.app-shell` (`display:flex; flex-direction:column; min-height:100vh`, `.content{flex:1}`) — this is what keeps the footer pinned to the viewport bottom on short pages and pushed below content on tall ones, with no manual height math. Keep any new top-level page wrapper inside `.content` rather than outside `Layout`, or this breaks.

`src/lib/indicators.ts` also has `ema()`/`macd()` (standard MACD(12,26,9): `ema(closes,12) - ema(closes,26)`, signal = `ema(macdLine,9)`) alongside the existing `sma()`/`rsi()` — same pure-function, no-backend-round-trip pattern, consumed by `AssetDetail.tsx`'s Teknikler tab.

**Per-user watchlist scoping**: `Asset.is_default` (seeded BIST tickers, `True`) vs. a `WatchlistItem(user_id, asset_id)` join row (created on `POST /assets/track`) is what determines visibility — `asset_service.list_visible_assets(db, user)` returns default assets ∪ the given user's own watchlist, and is used by `GET /assets`, `GET /assets/quotes`, and `GET /assets/search`'s `already_tracked` flag. `routers/auth.get_current_user_optional` (returns `User | None`, never raises) is what lets those endpoints stay public while still personalizing for a logged-in caller — `track_asset` itself requires real auth (`get_current_user`) since tracking is what writes the `WatchlistItem`. The underlying `Asset`/`PriceHistory` rows stay in one shared pool regardless (price data is fetched/cached once, not per user) — only *listing* is scoped, not the per-symbol `/assets/{ticker}/analysis` endpoint, which stays open to any known ticker (bookmarkable links to a symbol you don't personally track still work, same as most real market-data sites). `asset_service.list_assets()` (no visibility filter) still exists for infra-only callers (refresh-all, the background auto-refresh loop) that must touch every asset regardless of ownership. `SymbolSearch.tsx`'s "Ekle" redirects a logged-out user to `/portfolio` (state: `{addAfterLogin}`) rather than failing with a 401; `PortfolioBuilder.tsx` completes that pending add once the user lands there authenticated.

**MSSQL boolean comparisons**: use `Column == True`/`== False` for boolean filters, never SQLAlchemy's `.is_(True)` — it compiles to `IS 1` on the mssql dialect here, which is invalid T-SQL (`IS` is for NULL checks, not boolean literals) and only fails at runtime against real MSSQL, not against the SQLite used in tests. This bit us once with `Asset.is_default`; watch for the same trap on any other boolean column.

**Auth hardening**: `services/rate_limit.py` has two independent limiters, both in-memory (per-process, not shared across workers — see its own module docstring for the multi-worker caveat). `is_locked_out`/`record_failed_attempt`/`reset_attempts` are the original email-keyed login limiter (5 failed attempts per email within 15 minutes locks that email out for 15 minutes, `routers/auth.py`'s `/login`). `throttle(max_calls, window_seconds)` is a generic FastAPI dependency factory (`Depends(rate_limit.throttle(10, 300))`), keyed by IP + the endpoint's own path, applied to expensive/public endpoints that hit Yahoo Finance or otherwise do real work per call: `/assets/track`, `/assets/{ticker}/refresh`, `/assets/refresh-all`, `/auth/register`, `/auth/2fa/verify`, `GET /public/portfolios/{token}/analysis`. `RegisterRequest.password_strength` (a Pydantic `field_validator`) enforces min-length-8 + at least one letter + one digit; `api.ts`'s `parseErrorDetail` unwraps FastAPI/Pydantic's `detail: [{msg, ...}]` validation-error shape (stripping the `"Value error, "` prefix Pydantic adds) into a plain readable string — reuse that pattern for any new validated endpoint rather than showing `[object Object]`.

**Auth: sessions, 2FA, audit log**: auth is no longer a bare stateless JWT. `auth_service.issue_token_for_user(db, user, user_agent, ip_address)` — used by `/auth/register`, `/auth/login` (when 2FA is off), and `/auth/2fa/verify` — mints a `jti` (uuid4), writes a `UserSession` row for it, and embeds the `jti` in the JWT payload alongside a `purpose: "access"` claim. `routers/auth.get_current_user_and_session` (which `get_current_user`/`get_current_user_optional` are now built on) decodes the token, then looks up the `UserSession` by `jti` and 401s/returns-`None` if it's missing or `revoked_at` is set — this is what actually makes a session revocable; a JWT's own `exp` can't be canceled early, so without this DB check a "logged out everywhere" action would be cosmetic only. `touch_session()` bumps `last_seen_at` but only if it's gone stale by 5+ minutes, to avoid a DB write on every single authenticated request. `GET/DELETE /auth/sessions`, `POST /auth/sessions/revoke-all-others` back the "Aktif Oturumlar" panel in `AccountSettings.tsx` (`SessionsSection`) — each row shows raw `User-Agent`/IP/last-seen, with a "Bu cihaz" badge on the session matching the request's own `jti`; no user-agent-parsing library is used, the raw string is shown as-is.

2FA is TOTP (`pyotp` + `qrcode[pil]`, no SMS infra) — `User.totp_secret`/`totp_enabled` (secret is written at `POST /auth/2fa/setup` time but `totp_enabled` stays `False` until a real code is confirmed at `POST /auth/2fa/enable`, so a half-finished setup never gates login). `auth_service.totp_qr_data_uri()` renders the `otpauth://` URI as a PNG server-side and returns a `data:` URI directly — the frontend (`TwoFactorSection` in `AccountSettings.tsx`) just needs an `<img src>`, no QR-generation library of its own. When `user.totp_enabled`, `POST /auth/login` returns `{requires_2fa: true, challenge_token}` instead of a real access token — `challenge_token` is a short-lived (5 min), purpose-scoped JWT (`purpose: "2fa_challenge"`, no `jti`/session row) redeemable exactly once at `POST /auth/2fa/verify`; `LoginForm.tsx` renders a second code-entry screen when it sees `requires_2fa`. `POST /auth/2fa/disable` requires both the current password and a fresh code, not just one or the other.

`services/audit_service.log_action(db, user_id, action, detail=None)` is an append-only insert into `AuditLog`, called from `portfolio_builder_service`'s create/update/delete/share, `portfolio_service`'s holding create/update/delete/sell, and `auth.py`'s password/email change, 2FA enable/disable, and session revocation — `GET /auth/activity` returns the latest 100, rendered by `AccountSettings.tsx`'s `ActivitySection` via a small local `ACTIVITY_LABELS` TR/EN lookup (not i18next — the action codes contain dots, which conflict with i18next's default key-nesting separator).

**Risk-scenario helpers are client-side, not new endpoints**: `frontend/src/lib/risk.ts` (`beta()`, `STRESS_SHOCKS`) computes portfolio beta straight from the already-fetched `analysis.portfolio_index`/`analysis.benchmark` series in `PortfolioBuilder.tsx`'s `StressTestSection` — no backend round-trip. `RebalancingSection` (same file) is the one exception that does its own fetch (`getHoldingsValuation`), compares real holdings market value against the portfolio's target weights, and only renders rows where the drift exceeds 2 percentage points; it re-fetches when `HoldingsPanel`'s `onHoldingsChanged` bumps a `holdingsVersion` counter in the parent (`PortfolioBuilder.tsx`), which is how the rebalancing table stays in sync after adding/editing/deleting a position without a full portfolio reselect. `RiskAlerts.tsx` is the shared alert-list renderer for both the portfolio-level (`buildPortfolioAlerts`) and asset-level (`buildAssetAlerts` in `AssetDetail.tsx`) conditions — all thresholds are computed from real data already in hand (volatility, drawdown, Sharpe, correlation, 52-week proximity, RSI); this is explicitly framed as in-app alerts, not push/email notifications, since there's no such infra here.

**Print/PDF**: `PortfolioBuilder.tsx` has two separate PDF paths, kept side by side rather than one replacing the other. "Yazdır / PDF Kaydet" is still just `window.print()` — the `@media print` block at the end of `App.css` hides chrome and forces a white/black palette, letting the browser's own "Save as PDF" print destination handle it. "Rapor İndir (PDF)" (`handleExportPdf`) is a real generated report via `lib/pdf.ts`'s `generatePortfolioPdf()` (`jspdf` + `jspdf-autotable`) — a branded document (summary metric table, portfolio-index + allocation chart images, weights table, correlation matrix) independent of whatever's currently visible on screen or the browser's print styling. The chart images come from the already-rendered Chart.js canvases via `chart.toBase64Image()` (`LineChart.tsx`/`DonutChart.tsx` are `forwardRef`-wrapped specifically so `PortfolioBuilder.tsx` can hold refs to the underlying `Chart` instances), not a second rendering pass and not `html2canvas`. `lib/pdf.ts` is dynamic-`import()`ed only inside `handleExportPdf` — jsPDF (+ its own optional `html2canvas`/DOMPurify transitive deps) is a real ~150kB-gzip weight, and eagerly importing it grew the `PortfolioBuilder` chunk from ~48kB to ~480kB; dynamic import keeps that cost paid only by someone who actually clicks the button.

**Code-split routes**: `App.tsx` lazy-loads everything except `Home`/`LoginForm` (`React.lazy` + a single `<Suspense>` around `<Routes>`) — `/market` and `/portfolio` pull in Chart.js/framer-motion/the candlestick canvas, which otherwise bloated the single main bundle past Vite's 500kB warning threshold. Keep new heavy per-page dependencies (a charting lib, a large icon set) behind the existing lazy route boundary rather than importing them from a shared/eager module.

**Mixed-currency FX conversion**: `market_data_provider.get_fx_rate(from_currency, to_currency)` does a best-effort Yahoo Finance `"{FROM}{TO}=X"` lookup (cached like `fetch_ohlcv_cached`), returning `None` rather than fabricating a rate on failure. `portfolio_service.value_holding()`/`valuation_summary()` always additionally compute TRY-normalized totals (`*_try` fields, `AGGREGATE_CURRENCY = "TRY"`) alongside the native-currency ones — the native totals stay the primary display for a single-currency portfolio, but a mixed-currency one now shows the TRY totals instead of the old "—" placeholder (`fx_unavailable` flags when some holding's rate couldn't be resolved, so the frontend can caveat rather than silently under-count). `PortfolioBuilder.tsx`'s `RebalancingSection` switches to the `_try` fields for its weight math whenever `summary.mixed_currency` is true.

**Sector tags**: `Asset.sector` (nullable) is a real yfinance value (`market_data_provider.get_sector()`, via the slower `.info` endpoint) — fetched once at track/first-refresh time, never fabricated, `None` shown as "Bilinmiyor" in the UI rather than guessed. `AssetScreener.tsx` has a sector filter dropdown + column; the Piyasa Görünümü cards show it as a small badge. `analysis_service.group_weights_by_attribute()` sums portfolio weight by an arbitrary per-asset attribute (unmapped values grouped under "Bilinmiyor" rather than dropped, so the breakdown still accounts for 100%) — `routers/portfolios.py`'s `/portfolios/{id}/analysis` uses it twice (sector, currency) to return `sector_allocation`/`currency_allocation`, rendered via `components/ExposureBreakdown.tsx` (a shared donut-chart-+-legend component, hidden when there's fewer than 2 distinct rows — a single-sector or single-currency portfolio has nothing to break down) in `PortfolioBuilder.tsx`'s `ExposureSection` ("Sektör ve Döviz Dağılımı"). `portfolio_service.sector_allocation(valued_holdings)` is the second, real-money caller of `ExposureBreakdown` — unlike the per-portfolio one (weighted by *target* weights), this weights by each holding's actual current TRY-normalized market value across every portfolio combined (pre-dividing by the priced total before calling `group_weights_by_attribute`, so the summed output is already the fractions that component expects), returned as `sector_allocation` on `GET /holdings/valuation` and rendered in `Home.tsx`'s `NetWorthSection` as "Sektör Dağılımı (Tüm Portföyler)".

**Temeller tab (fundamentals, analyst recommendations, earnings calendar, institutional holders)**: `/assets/:ticker`'s fourth tab, "Temeller", is backed by a single combined `GET /assets/{ticker}/fundamentals` route (public, no auth, no `response_model` — same shape as `/assets/{ticker}/analysis`) rather than four separate endpoints, since it powers one tab and this avoids extra round-trips. `market_data_provider.py` gained four cached getters (`get_fundamentals`, `get_recommendations_trend`, `get_earnings_calendar`, `get_institutional_holders`), each following the module's existing two-tier (in-process + Redis) cache pattern with a 6h TTL — matching `get_market_cap`'s rationale that this is reference/display data, not something that needs to be live-fresh. `get_fundamentals` is one `.info` call covering trailing/forward P/E, price/book, price/sales, profit margin, ROE, debt/equity, dividend yield, beta, and the analyst target-price range + consensus key; `get_recommendations_trend` parses `Ticker.recommendations` (strong buy/buy/hold/sell/strong sell counts by recent period, rendered as a `DonutChart` for the latest period); `get_earnings_calendar` parses `Ticker.calendar`'s `"Earnings Date"`/`"Earnings High/Low/Average"`/`"Revenue High/Low/Average"` keys; `get_institutional_holders` combines `Ticker.major_holders` (insider/institution ownership %, keyed by `insidersPercentHeld`/`institutionsPercentHeld` with a `Value` column) and `Ticker.institutional_holders` (top holders table: holder, shares, % of shares outstanding, date reported). Every field is `None`/empty when Yahoo doesn't have it — never fabricated — which is the common case for BIST tickers specifically (Yahoo's analyst/institutional coverage of BIST is thin; a US large-cap tracked via the dynamic asset universe will have much richer data here). **A real yfinance scale quirk found while building this**: `dividendYield` in `.info` comes back already percent-scaled (e.g. `4.05` meaning 4.05%), unlike `profitMargins`/`returnOnEquity` which are true fractions (e.g. `0.316` meaning 31.6%) — confirmed empirically against real BIST tickers. The frontend formats `dividend_yield` as a raw number + `%` (not through the `formatFraction()` helper used for margin/ROE, which would double-scale it); watch for the same inconsistency if a new `.info` field is added here.

**Global economic indicators (`/enflasyon`)**: what was originally an inflation-only page is now a 3-tab "Küresel Ekonomik Göstergeler" globe (Enflasyon / GSYH Büyümesi / İşsizlik) sharing one d3-geo globe + leaderboard shell — `backend/services/worldbank_service.py` (renamed from `inflation_service.py` once it grew beyond inflation) generalizes the original single-indicator fetch into `get_indicator_by_country(key)` keyed against `_INDICATORS = {"inflation": "FP.CPI.TOTL.ZG", "gdp_growth": "NY.GDP.MKTP.KD.ZG", "unemployment": "SL.UEM.TOTL.ZS"}`, with `get_inflation_by_country()`/`get_gdp_growth_by_country()`/`get_unemployment_by_country()` as thin wrappers and one cache entry per indicator key (24h TTL each, same as before). `routers/markets.py` exposes this as `GET /markets/inflation` (unchanged path, for backward compatibility) plus new `GET /markets/gdp-growth` and `GET /markets/unemployment`, all sharing one generalized `CountryIndicatorValue` Pydantic model. `InflationMap.tsx` picks bands (and their colors) per indicator rather than reusing one scale — inflation and unemployment read "lower is better" (green→red as the value climbs), GDP growth reads the opposite way (red for a contraction, green/gold for strong growth) — via a `HIGHER_IS_BETTER` map that also flips which end of the highest/lowest leaderboard cards renders green vs. red.

**Temettü Takvimi (`/temettuler`, real dividend payment history — not a forward calendar)**: `portfolio_service.dividend_history()` walks every currently-open holding, grouped by ticker (so multiple lots of the same stock don't produce duplicate rows), and intersects each ticker's real per-share payment history (`market_data_provider.get_dividends()`, yfinance's own data) against which lots were already purchased by each pay date — a lot bought after a given ex-dividend date doesn't count toward that payment. `GET /holdings/dividends` returns these real, already-happened payments (ticker, date, per-share amount, quantity credited, total, TRY-normalized via a real spot FX rate) sorted newest-first. There is deliberately no "upcoming dividend" feature here: yfinance's dividend data is historical only, and this project doesn't fabricate a projected payment date/amount from it — `pages/DividendCalendar.tsx` is explicit in its own copy that this is a payment history, not a calendar of future payments. Linked from `Home.tsx`'s `NetWorthSection` (next to the aggregate "Temettü Geliri" figure) and from `HoldingsPanel.tsx`'s "Pozisyonlar" header, not from the main topbar nav — same treatment as `/uyarilar`, an authenticated per-user view that doesn't need a permanent nav slot.

**Piyasa Haberleri (real news, no fabricated headlines)**: `market_data_provider.get_news(yahoo_symbol)` wraps yfinance's `Ticker.news` — title, summary, publisher, publish time, article link, and thumbnail are all real fields straight from Yahoo Finance's own feed, cached 15 min like `fetch_ohlcv_cached`. `GET /markets/news` (`routers/markets.py`) fans this out concurrently (`ThreadPoolExecutor`, same pattern as `/markets/crypto`) across a fixed `NEWS_SYMBOLS` list (major BIST tickers + `^GSPC` + `BTC-USD` — the BIST 100 index symbol itself, `XU100.IS`, was checked and carries no news of its own), dedupes the same syndicated story appearing under multiple symbols (by id, then by title as a fallback), and returns the newest 12. `MarketNewsPanel.tsx` on the homepage renders these as link-out cards (opens the original article in a new tab, standard news-aggregator attribution — publisher name + short teaser + link, not full article text) with a client-computed relative time ("38 dk önce"); a card with no thumbnail just omits the image rather than showing a broken one. Updates live over the shared WebSocket's `news` channel (see "Auto-refresh (backend) / live data" above) rather than polling; the whole section is hidden (not an error banner) if the feed comes back empty.

**Net Değer Geçmişi (real net-worth-over-time)**: `GET /holdings/value-history` (`portfolio_service.holdings_value_history()`) reconstructs total market value and cost basis *over time* purely by combining each currently-open `Holding` lot's quantity/purchase date/purchase price with the asset's already-stored daily `PriceHistory` — no snapshot table, no cron/background job, since the close-price history already lets us compute what today's positions were worth on any past trading day they'd already been bought by. A mixed-currency holding is converted using the real *historical* daily FX rate for each date (`market_data_provider.fetch_ohlcv_cached("{FROM}TRY=X")`, not today's spot rate applied retroactively) — a currency whose historical FX series can't be fetched is excluded from the totals and named in the response's `excluded_tickers`, with `fx_unavailable: true`, rather than silently mis-summed. This is deliberately *not* a full historical audit trail: only currently-open lots are traced back to their purchase date, so a since-fully-sold position contributes nothing and a partially-sold lot is shown at today's (already-reduced) quantity for its whole holding period — `Home.tsx`'s `NetWorthHistoryChart` (in the "Net Değer Özeti" section, only rendered once there are 2+ points) surfaces this as an explicit caveat line rather than presenting the curve as complete. Same 1A/3A/6A/1Y/Tümü client-side range-tab slicing pattern as the homepage's BIST 100 hero chart and every other range-tabbed chart in the app.

**Portfolio comparison**: `PortfolioComparisonSection` in `PortfolioBuilder.tsx` (renders only when the user has 2+ portfolios) overlays each selected portfolio's `portfolio_index` (already base=100) on one `LineChart` — no new backend endpoint, just `Promise.all` over the existing per-portfolio `getPortfolioAnalysis()`, with a per-portfolio `.catch(() => null)` so one broken portfolio (e.g. no price data) doesn't blank out the whole comparison.

**Untracking is persistent**: the X button on a Piyasa Görünümü card calls `DELETE /assets/{ticker}/track` (→ `asset_service.remove_from_watchlist`) for a non-default asset, not just a client-side `displayedTickers` filter — so it stays gone after reload/relogin, not just for the session. Default assets can't be untracked this way (400) since they aren't in anyone's `WatchlistItem` row to begin with; removing one from view is still session-only, unchanged. Re-adding a previously-untracked asset via the "Varlık Ekle" picker calls the lightweight `POST /assets/{ticker}/watchlist` (`rewatch_asset`) rather than the full `/track` flow, since the `Asset` row and its price history already exist — no yahoo_symbol/name/exchange payload needed, just re-link the existing asset to the user.

**yfinance data quirks `fetch_ohlcv` guards against**: (1) today's still-forming session (or a no-trade day for a thin ticker) can come back with `NaN` OHLC values — MSSQL's pyodbc driver rejects `NaN` outright and fails the *entire* batch insert, not just that row, so `fetch_ohlcv` does `history.dropna(subset=["Open","High","Low","Close"])` before returning. (2) a fixed lookback window (`period="1y"`) can come back completely empty for a real, valid symbol (was seen with real BIST tickers, not just recent IPOs) even though Yahoo does have history — `fetch_ohlcv` retries once with `period="max"` before raising. Both were the actual root cause behind "No price data for X" errors users hit when tracking a new symbol — if that error resurfaces, check for a similar not-yet-handled yfinance edge case rather than assuming the symbol truly has no data. Relatedly, `routers/assets.py`'s `track_asset` only calls `asset_service.add_to_watchlist()` *after* the price backfill succeeds (or already existed) — never before — so a failed backfill doesn't strand a dataless asset in the user's watchlist that they can then neither see (analysis 404s) nor retry (search would show it as already tracked).

**Windows dev-server process hygiene**: `uvicorn --reload` in this environment spawns its reloaded worker under a *different* Python interpreter than the one the parent was launched with (`AppData\Local\Programs\Python\Python311\python.exe`, not the project's `venv`), and repeated restarts can leave orphaned worker processes that `Get-CimInstance Win32_Process | Where CommandLine -like '*uvicorn*'` fails to enumerate (silently missing zombies), while one keeps squatting on port 8000 serving stale code. If a backend change doesn't seem to take effect no matter how many times you "restart" it, don't trust `Win32_Process` alone — cross-check with `Get-NetTCPConnection -LocalPort 8000` for who's actually listening, and use `Get-Process -Name python | Stop-Process -Force` (not WMI CommandLine filtering) to reliably kill every interpreter before relaunching exactly one instance.

**No real company logos**: rather than embedding actual company logos (trademarked assets this project has no license to redistribute), every ticker gets a deterministic colored monogram avatar instead — `src/lib/avatar.ts` (`avatarColorFor`/`avatarInitials`, hashes the ticker into a fixed palette) + `src/components/TickerAvatar.tsx` (the `.ticker-avatar` CSS class, works in both the plain-CSS and Tailwind pages since it's just inline-styled). Reuse `TickerAvatar` for any new per-asset UI instead of sourcing a real logo.

API base URL comes from `VITE_API_BASE_URL` (defaults to `http://localhost:8000`). CORS is env-driven: `config.settings.cors_origins` (a `CORS_ORIGINS` comma-separated env var, default `http://localhost:5173`) feeds `main.py`'s `CORSMiddleware` via `cors_origins_list` — set it in `backend/.env` for any deployment beyond local dev rather than editing `main.py`.

**Deployment**: the frontend and backend deploy to two different kinds of host, since the backend is a long-running process (WebSocket connections, `asyncio` background loops — see "Auto-refresh") that a serverless platform like Vercel can't run; Vercel is used for the frontend only. `frontend/vercel.json` is a plain SPA rewrite (`/(.*) → /index.html`) so a hard refresh on a client-side route like `/portfolio` doesn't 404; set `VITE_API_BASE_URL` in the Vercel project's env vars to the deployed backend's URL (`LiveDataContext.tsx`'s `WS_BASE` derives the WebSocket URL from this same value by swapping `http`→`ws`, so one env var covers both REST and WebSocket). `render.yaml` (repo root) is a Render Blueprint for the backend: a `python` web service (`rootDir: backend`, `uvicorn main:app --host 0.0.0.0 --port $PORT`) plus a managed free Postgres database, wired together via `DATABASE_URL` (see `config.py`'s override above) — `JWT_SECRET_KEY` is auto-generated by the blueprint, `CORS_ORIGINS` is set to the real deployed Vercel URL. Optional integrations (`SENTRY_DSN`, `SMTP_*`, `REDIS_URL`, `VAPID_*`) aren't part of the blueprint — add them as Render env vars only if that integration is wanted in the deployed environment. `PYTHON_VERSION` is pinned (`3.11.9`, matching the version `requirements.txt`'s pins were resolved against) — **required**, not cosmetic: Render's default Python is newer than what `pandas`/`numpy`/`scipy`'s pinned versions ship prebuilt wheels for, so without this pin `pip install` silently falls back to compiling each of them from source, which is dramatically slower (scipy alone took over 15 minutes before its build-dependencies step was cancelled in practice) and depends on a Fortran/BLAS toolchain being present in the build image at all. If a future dependency bump reintroduces multi-minute-plus "Preparing metadata (pyproject.toml): still running..." lines in the Render build log, check for the same missing-wheel mismatch before assuming the build is merely slow.

**Reference-data endpoints (`backend/routers/markets.py`)**: FX pairs, a curated crypto list, an indices-and-metals ticker strip, and country-level economic indicators (inflation, GDP growth, unemployment) are deliberately *not* modeled as trackable `Asset` rows — they're fixed reference lists with no watchlist scoping, no DB persistence, no auth. `market_data_provider.get_quote(yahoo_symbol)` (built on `fetch_ohlcv_cached`) gives last price + daily change for a symbol without needing an `Asset`/`PriceHistory` row at all, used by `GET /markets/fx` (`FX_PAIRS`), `GET /markets/crypto` (`CRYPTO_SYMBOLS`, ~55 coins, fetched concurrently via a `ThreadPoolExecutor` — sequential fetches took ~40s cold, the pool gets it to roughly the slowest single request instead of the sum of all of them; each quote also carries `market_cap` via the cached `get_market_cap()`, and the endpoint sorts by it descending — most valuable first, unresolved caps sink to the bottom rather than being dropped), and `GET /markets/ticker-strip` (`TICKER_STRIP_SYMBOLS` — BIST 100, USD/TRY, EUR/TRY, Bitcoin, Ethereum, gold; note gold is `GC=F` (COMEX futures), since the more obvious `XAUUSD=X`/`XAU=X` spot-gold symbols don't resolve on Yahoo). `GET /markets/inflation`/`/markets/gdp-growth`/`/markets/unemployment` are different in kind: they're the only endpoints in this app that don't touch Yahoo Finance at all — `backend/services/worldbank_service.py` calls the World Bank's free, key-less Open Data API and cross-references the country-list endpoint to filter out region/income-group aggregates, caching each indicator for 24h since it's annual published data, not a live tick — there is no such thing as "live" inflation/GDP/unemployment anywhere, so the UI always shows each country's own latest published year rather than implying real-time. See "Global economic indicators" below for the frontend side.

Frontend: `components/LiveTickerStrip.tsx` (an infinite CSS-marquee price strip at the top of `Home.tsx`, own component/own theme tokens — not a TradingView embed; TradingView's free widget renders in a cross-origin iframe that this app's CSS categorically cannot restyle, which is exactly why this is hand-built against `/markets/ticker-strip` instead), `pages/CryptoLeaderboard.tsx` (`/kripto` — top-5 gainers/losers plus the full market-cap-sorted list; gainers/losers are filtered to `change_percent > 0`/`< 0` rather than blindly slicing top/bottom 5, so a day where the whole curated list is green doesn't mislabel "least-up" coins as "losers"), and `pages/InflationMap.tsx` (`/enflasyon` — a real rotating, drag-to-spin orthographic globe, hand-rolled with `d3-geo`'s `geoOrthographic`/`geoPath`/`geoGraticule10` plus `topojson-client`'s `feature()` over the `world-atlas` `countries-110m.json` topology bundled at build time; no `react-simple-maps`, no runtime map-tile fetch. Rotation auto-advances on a throttled `setInterval` — not raw `requestAnimationFrame` — pausing on hover (so the tooltip target holds still) and on drag; each feature's numeric ISO-3166-1 `id` is joined to the World Bank's alpha-3 country codes via `i18n-iso-countries`'s `numericToAlpha3`. A handful of the 110m topology's features share a duplicate or missing `id`, so the per-country `<path>` key is `` `${id}-${index}` ``, not the bare id — using the bare id was a real bug that flooded the console with React key-collision warnings on every animation tick and made the page feel frozen.) `d3-geo`/`topojson-client`/`i18n-iso-countries`/`world-atlas` all needed `--legacy-peer-deps` at install (some haven't declared React 19 support). An earlier version of the globe used `react-simple-maps`, which pulled in a `d3-color` version with a known ReDoS advisory (patched via a `package.json` `overrides` entry at the time) — both `react-simple-maps` and that override were removed once the globe moved to hand-rolled `d3-geo`/SVG, since neither was needed anymore. If you reintroduce a mapping library, re-check `npm audit`.

**Price precision is 8dp, not 2**: `market_data_provider.fetch_ohlcv`'s `OhlcvBar` rounds OHLC to 8 decimal places, not 2 — it used to be 2dp, which was fine while every tracked asset was a share price but silently zeroed out sub-cent crypto (SHIB was rendering as a flat "$0.00" and its daily change as a fabricated-looking "0.00%"). If you add another asset class with its own price scale, check whether 2dp-era assumptions have crept back in anywhere before trusting a displayed "0.00".

**Auth model**: `/assets*` endpoints are public (read-only market data, including `/assets/{ticker}/refresh` and `/assets/refresh-all` which hit Yahoo Finance). `/portfolios*` and `/holdings*` require a Bearer JWT (`Depends(get_current_user)`, now session-checked — see "Auth: sessions, 2FA, audit log") and are scoped to the authenticated user; `GET/PUT/DELETE /portfolios/{id}` all 404 if the portfolio doesn't belong to the caller. `/public/*` (`routers/public.py`) is the one exception scoped to a *token*, not a user — see "Portfolio sharing".
